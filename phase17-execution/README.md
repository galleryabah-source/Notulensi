# Phase 17-E — Execution & Evidence

This directory contains the production-readiness evidence protocol.

## Rules

1. Source-code gates are not runtime evidence.
2. Evidence must be generated by an actual execution environment.
3. `PASS` requires an artifact reference.
4. `FAIL` requires the observed failure to be preserved.
5. `BLOCKED` means a prerequisite prevents a valid test.
6. `NOT_RUN` is never interpreted as `PASS`.
7. No evidence file may contain secrets, API keys, passwords, access tokens, or raw sensitive prompts.
8. Legacy retirement remains prohibited until an independent retirement decision is approved.
9. Production activation remains fail-closed while required evidence is absent.

## Evidence lifecycle

`NOT_RUN -> RUNNING -> PASS | FAIL | BLOCKED`

A failed or blocked check must enter the remediation track before a final Go decision.

## Minimum evidence categories

- repository integrity
- static validation
- cross-phase consistency
- runtime health
- database behavior
- authentication/RBAC
- security regression
- AI provider and cost controls
- observability
- backup/restore
- disaster recovery
- performance
- rollback/canary
- release metadata

## Authentication/RBAC boundary discovery

`auth-boundary-audit.mjs` is a discovery gate, not an authentication implementation. It records whether the repository contains the previously defined authentication/RBAC contract artifacts and whether an executable server/runtime boundary is discoverable.

Contract artifacts such as `phase13.3`, `phase13.4`, `phase14.4`, `phase14.5`, `phase15.4`, and `phase15.5` are evidence of design/contract intent only. They must not be promoted to runtime `PASS` without actual login/session/authorization execution.

If no executable authentication boundary exists, the resulting domain remains `17-E.runtime.auth = NOT_RUN` and the production-readiness gate remains fail-closed.

The manifest template is intentionally incomplete and must never be edited to fabricate successful runtime results.
