# Phase 17-E R2.2 Authentication/RBAC Compatibility Audit

Status: INTEGRATION_REQUIRED
Baseline: `phase17-execution-evidence` at `f9432e902bc2992826bfb290596d27a4e9c4ee3a`
Historical source: `phase4.9-authentication-accounts`

## 1. Historical runtime implementation confirmed

The historical authentication implementation is executable server code, not a source-only contract. `backend/src/auth.js` performs Bearer-token extraction, JWT verification with HS256, optional issuer/audience validation, UUID validation of `sub`, PostgreSQL user lookup, active-account enforcement, and population of `req.user` / `req.account`.

The historical server protects `GET /api/account/me` and share-management endpoints with the authentication middleware. Authorization for private shares uses the authenticated user ID and an `admin` role check.

## 2. Compatibility findings

### 2.1 Runtime placement mismatch

The Phase 17 evidence baseline is currently a static/evidence-oriented repository surface with the Phase 17 execution harnesses. The historical auth implementation lives under a separate backend/server runtime lineage. Therefore it cannot be treated as already wired into the Phase 17 runtime merely because its source exists in Git history.

### 2.2 Dependency/runtime mismatch

The historical Phase 4.26 runtime lineage has its own `package.json`, Node >=20 requirement, PostgreSQL dependency, server entrypoint, migrations, repositories, and security tests. The Phase 17 evidence branch must not assume those runtime dependencies are present until they are explicitly integrated and executed.

### 2.3 Role-model mismatch

The historical database model uses roles `user` and `admin`. The Phase 14 authorization boundary contract currently declares `OWNER`, `ADMIN`, `EDITOR`, `REVIEWER`, and `AUDITOR`. This is a semantic compatibility issue, not a reason to silently rewrite the historical implementation. A mapping must be explicitly designed and tested before R2.2 can claim RBAC compatibility.

### 2.4 Authentication contract mismatch

The historical JWT implementation requires `JWT_SECRET` of at least 32 characters and supports optional `AUTH_ISSUER` and `AUTH_AUDIENCE`, while restricting algorithms to HS256. These runtime requirements must be supplied as controlled CI test configuration and must never be committed as production secrets.

### 2.5 Data-model coupling

The historical authenticated share API depends on `users`, `documents`, `document_revisions`, `document_shares`, and `share_access_logs`. The R2.2 harness therefore needs an ephemeral PostgreSQL schema/data set compatible with the actual server implementation rather than a mocked identity layer.

## 3. Integration decision

Do NOT merge `phase4.9-authentication-accounts` wholesale.

Do NOT create a fake authentication server solely for the evidence collector.

The next implementation step is a controlled port/integration of the smallest compatible historical server/auth surface into the Phase 17 runtime harness, preserving the historical authentication semantics while defining and testing the role mapping required by the current authorization contract.

## 4. Required runtime evidence

The eventual CI artifact must record actual HTTP results for:

1. missing Authorization header -> 401;
2. malformed/invalid JWT -> 401;
3. valid JWT for active controlled identity -> authenticated endpoint succeeds;
4. valid JWT for inactive controlled identity -> 401;
5. authorized role/resource operation -> success;
6. unauthorized role/resource operation -> 403/deny according to the actual API contract;
7. evidence of account identity resolved from PostgreSQL;
8. no production secret material in repository or artifact;
9. readiness remains fail-closed until R2.2 is genuinely executed.
